# 共用刀表規格

欄位／共用核心契約版本 **1.3.0**，正式來源是 `contracts/sheet-contract.json`。Calendar 監控另採 **1.4.0** 執行規則；GAS 的日期部署版號另行維護。

| 來源 | 用途 |
| --- | --- |
| contracts/sheet-contract.json | 1.3.0 欄位、別名、日期、院區、ID 與共用解析基準 |
| contracts/calendar-monitor-policy.json | 1.4.0 監控執行規則；僅覆蓋監控的衝突處置，補充確認狀態、觀察及刪除保護 |
| contracts/cases/ | 實際 GAS 匯出的合成解析、寫入與封存案例 |
| packages/python/src/vghks_sheet_core/ | Python 共用解析、永久識別、共享基準與 Calendar 資料模型 |
| tools/generate_contract.py | 生成 GAS CONFIG、Python 內嵌 JSON 與案例 |
| contracts/consumers.json | 部署前交叉驗證的固定主程式候選 commit |

## 共通行為

- 依表頭名稱定位，保留自訂欄、公式、註記及人工保護。
- 日期與院區由最近有效刀日決定。**月份患者醫院欄為可選人工內容；新列留白，不補填、不覆寫，搬列保留。** FU 使用自身醫院及日期。
- ScheduleSyncId、CalendarEventId 隨整列搬移。共用核心、主程式及 GAS 寫入器遇重複／孤立 ID 維持嚴格拒絕；監控依下方 1.4.0 規則隔離可明確界定的衝突群組。刀日結構不明仍停止整份同步。
- Calendar 以這兩個 ID 追蹤原排程；既有可信紀錄的病歷號或姓名至少一項相符，即可保留綁定。換院區可先清空病歷號，之後填入新院區號碼；同姓名可延續原事件，空值照實同步，絕不從快取回填。姓名、病歷號皆不符時只暫停該列。主程式的臨床病歷號比對仍維持嚴格核對。
- 單列日期／病人綁定／事件格式問題只略過該列，其餘列繼續；顯示分頁、列號與原因，不顯示臨床值。該輪禁用全部刪除並重設缺列確認；整份結構歧義、主機衝突、封存鎖及共用連線／授權錯誤仍停止同步。
- 取消依病歷號的顯示刪節線判定，含富文字。
- 獨立監控依刀表目前日期，只同步台北時間今天起的月份排程及 FU／All；已完成同步且仍在過去的排程不查詢或變更日曆。刀日與無日期 FU 不建事件。
- 刀表仍完整讀取排程 ID，以保護跨月搬移、封存及刪除確認；不依月份名稱推斷排程日期。過去排程改到今天或未來時，恢復同步並更新原本綁定的日曆事件，沿用兩個 ID；舊快取日期與歷史保護標記不阻擋改期。缺列且已過去或日期不明的事件仍保留。
- 今天／未來改到過去時，更新原綁定事件一次，回讀核對並保存完成狀態後略過；待核對操作失敗或重啟後續接同一事件，未確認前不能當作已完成。原事件不存在時保留綁定，不補建過去事件。自然進入過去且沒有待核對操作的排程仍略過。
- 刀表以固定唯一 metadata 登記一台主機，核對本機識別與監控識別；第二台主機或複製的資料庫均拒絕同步，不提供自動接替。
- 封存保留 ID；未完成封存阻擋寫入。只有連續兩輪完整成功且無單列錯誤的掃描確認缺列，才允許移除已確認擁有權、仍在今天或未來的事件；過去事件保留。

## 監控執行規則 1.4.0

`contracts/calendar-monitor-policy.json` 僅供獨立 Calendar 監控使用；其隔離規則優先於 1.3.0 `rules.identity` 的整份停止要求。共用解析器與主程式／GAS 寫入器仍拒絕衝突，不改欄位格式、ID 格式或臨床身分核對。

- 手動新列自動配置系統 ID；原生整列搬移保留兩個 ID、更新原事件。整列刪除後重打，即使同一患者也視為新排程；不以姓名、病歷號或內容相似度猜測配對。
- 重複、孤立、公式 ID 等衝突隔離所有相連列；刀日識別衝突連同整個刀日區塊隔離。孤立 ID 尚在時，未識別的可能目的列也保留待核對。僅在記憶體遮蔽這些列供嚴格規劃器使用，原始列不清除、不覆寫；正常列繼續。欄位／刀日結構不明仍整份停止。任何部分失敗均停止後續刪除並重設缺列計數。
- `desired_resource` 是來源預期；`resource` 只保存已確認的 Calendar 狀態。Calendar 寫入回讀成功就保存確認，即使 Sheet 綁定回寫尚未完成。舊版 pending 不可信任快取日期；來源仍在或已刪除，均先 GET 原事件。來源消失後不補做舊預期更新，以實際事件日期決定保留或刪除。
- 每 5 分鐘完整唯讀觀察來源；Calendar 維持每 60 分鐘同步。首次配置 ID 前及技術寫入後亦記錄觀察；本機保留最新快照、最近 200 次有變動觀察及最多 10,000 筆列變更。畫面只顯示列位置、日期／院區、欄位名稱及計數。這是讀取間淨變化，不是每次編輯紀錄，也不代表 Calendar 同步成功；觀察不累計刪除確認，刪除仍須兩輪完整成功的 Calendar 同步。
- 更新／刪除既有事件以實際 Calendar ETag 使用 `If-Match`。刪除前再讀刀表與事件，核對擁有權及今天／未來日期；缺少 ETag 或遇 412 保留事件並待下輪核對。已完成的跨事件操作不能整批回滾。

## 更新順序

1. 修改 JSON、對應實作與合成案例；新版患者欄位是否進入 Calendar 須明確定義。
2. 執行 `python tools/generate_contract.py`，核對生成差異及真實 GAS 匯出。
3. 跑 GAS 測試、`python -m vghks_sheet_core.verify --gas-repo .` 及固定主程式交叉驗證。
4. 欄位／共用核心更新時，主程式與監控固定同一個已驗證完整核心來源 commit，更新依賴鎖及契約 manifest，各自執行回歸。
5. GAS 部署等待相容性檢查；主程式 Release 使用成功 main 建置的原產物，監控另行發布與部署。

Python 套件隨部署保存規格，執行中不下載最新規格。兩個 Python 消費端的完整核心來源 commit、內嵌規格與案例皆需核對；GAS 的 consumer commit 是 CI 相容性候選，不是另一份規格來源。

僅調整監控執行規則時，核心 1.3.0 與既有欄位 JSON／生成檔保持不變，不要求主程式重建或 GAS 重新部署。監控 manifest 的 `contract_version`／`gas_revision` 固定共用欄位與核心，`policy_version`／完整 `policy_revision` 另固定監控政策來源。版本及發布可分開更新，相容性仍須驗證。

新增相容能力遞增 minor，修正遞增 patch；移除欄位／別名或改變識別、取消、刪除語意遞增 major。破壞性更新先發布可讀新舊格式的消費端，再遷移資料，最後移除舊格式。

1.3.0 增加缺值與跨院區病歷號的相容能力及單列隔離；永久 ID、臨床身分判定與刪除條件均保留。合成案例 `calendar_binding.json` 同時驗證舊版快取遷移、缺值、病歷號更換、拒絕不同病人及 FU 日期錯誤隔離。
